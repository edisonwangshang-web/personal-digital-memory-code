本文为公开工程实施方案，真实资料和验收留私库。本批dev28开发版仅dev验证、不更新master，默认11/9和普通quality0.15；来源0.1、正式知识0.2保持，旧10/8／0.12、恢复0.13和assembly0.14按原合同核验。本批补纯程序组装中断的零调用恢复，中断回归与准确dev CI待核；既有工程检查不替代真实全链，M1整体未验收，状态见[Roadmap](roadmap.md)。

## M1 知识质量与 Skill 接入批次

提取和独立审核实际加载不可变Skill、必要模板与共同质量规范，绑定资料覆盖、可复算描述统计、时间限定和逐项质量检查。extract@9／review@7还引用knowledge-context-v1，要求知识来源、时间、范围和已提供关系自足；current按明确object_paths读取，主题带精确record依赖。所选对象齐全不表示读遍原文或全库。来源与正式对象不迁移；历史规则及请求字节保留。字段见[质量契约](data-conventions.md#skill-quality-contract)，执行见[实现明细](implementation-details.md#skill-quality-execution)，验收见[SQ01—SQ11](scenarios-and-acceptance.md#skill-quality-acceptance)。

| 顺序 | 工程与实际验收 | 验收出口 |
| --- | --- | --- |
| 1. Skill 引用与实际加载 | 两角色分别解析固定版本及必要依赖，共享基础质量规范；实际内容、输出契约和请求一起绑定。缺失、摘要、角色或版本不符即阻塞 | SQ01—SQ03；核实际请求，不能只凭配置或模型自述 |
| 2. 输入清单与派生计算 | 程序按实际片段形成表格画像，记录列用途、日期、缺失／零值、重复及未完结日；按明确公式计算允许统计 | SQ04、SQ06；原始行可追溯，统计可重算，未知口径和不可比范围明确 |
| 3. 提取与独立审核 | 提取组织概览、分类、指标去向和时间状态；独立审核回看原文、画像、计算和候选，逐项给证据及结果 | SQ05、SQ07—SQ09；误读、遗漏、过时状态和错误关系反例被阻止；可修复问题返工，原意需用户决定才待确认 |
| 4. 发布、兼容与恢复 | 候选和审核绑定规则、覆盖、计算及精确版本；普通／分解审核全部义务通过后发布；旧链按原契约读取 | SQ10—SQ11；规则变化不能借旧Review发布，unknown与持久重试身份保留，完成节点核验复用 |
| 5. 限定真实质量验收 | 仅使用实际获准的来源，以新链加工、独立审核，复核指标覆盖、主题概览、时态、引用、目录与只读问答 | 适用SQ场景及真实模型证据；不预定对象数，不以旧规则通过结果代替新质量验收 |

质量验收纳入M1-01，并覆盖M1-02更新和M1-03同一加工链。普通返工及分解恢复按绑定支持0.10／0.11／0.12；历史0.9 operator入口`resume-unstarted-revision`和`revalidate-completed-extraction`缺新Skill证明，对新质量链须以`skill_quality_recovery_attestation_required`在模型前拒绝，不能降级。

可先人工触发capture→提取分类→独立Review→proof消费发布→目录／只读问答→恢复。同一有效已完成阶段核验复用，只对失败或规则改变影响的环节返工；unknown先对账。新queue默认auto，容量内单次Review，超限或显式decomposed-v1使用object／coverage／global完整证明；必要语义闭包仍超256000字节则blocked_capacity。人工成功不证明云任务已部署，也不完成M1。

## 1. 本轮要交付什么

**M0：一段获准真实资料保存并经审核发布后，独立调用仍能准确说明其内容、哪些细节尚无依据，并找到原话。**

**M1：围绕同一主题持续交资料，随时问答；提取加工与独立审核分别引用固定版本的 Skill，整理结果有来源、覆盖说明及正确时间状态；每日完成增量整理，补充和纠正能够更新知识，失败能够恢复。** M1 通过后，第一版知识库完成。数据可比时的可复算描述统计纳入知识整理，健康原因分析和个人建议留在 M2。

首版沿用 ChatGPT 入口、模型加工与独立 Review、程序控制发布、Markdown／私有 Git 和本地副本。建设顺序按完整业务闭环推进，每批贯通必要的四层模块。M0 手动触发，M1 在同一处理流程上接每日任务。

范围沿用总体方案：不建设独立 App、小程序、专门索引、图数据库、三个独立 Agent 服务、全平台历史自动采集或附件本体备份；个人分析、计划和复盘留在 M2—M4。

## 2. 实施方式与最小工程产物

开发和评审依据公库文档、已确定的方案和实际证据，不依赖上一轮聊天上下文。开发工具、用户交互入口、每日任务执行环境分别确定，不能因为开发环境能运行就视为每日任务可用。

**工程采用轻量Python程序组织模块，规则、提示词及Skill随版本管理，正式发布串行。** 环境探测仍须对每个目标运行环境完成；独立Review可用同一模型的独立调用，第二模型是另一个独立验收项。

| 对应层与模块 | 要交付的最小能力 | 首次落地 |
| --- | --- | --- |
| 第一层：多端采集、问答与确认 | 明确提交方式；区分保存回执、发布结果和待确认事项；问题、补充与纠正进入对应流程 | M0-02、M0-04 |
| 第二层：提取、Review、回答 | 三类独立调用及版本化规则；只向各调用提供必要证据；Review 返回可检查的结论和原因 | M0-03、M0-04 |
| 第三层：采集与 Git 适配 | 来源去重、按版本读取、条件写入、写后读回及成功回执 | M0-02 |
| 第三层：校验与发布控制 | 校验结构、引用与版本；审核绑定检查；允许路径限制；相关记录和 Wiki 一致提交 | M0-03 |
| 第三层：证据读取、流程编排 | 文件查找和证据集合；新原文与控制检查；持久进度、增量选择、有限重试与续跑 | M0-04 至 M1-04 |
| 第四层：文件与版本 | 最小模板、来源快照、候选、正式记录、主题页、审核与回执；可恢复本地副本 | 随各批次补齐 |

程序与适配放公库 `project/src/`，模板、规则和人工样例放公库 `project/`。可公开工程检查记录包含准确代码版本、输入类型、命令和结果；真实输入／输出、模型返回、审核、恢复及实际验收留私库，每批记录版本、实际结果和原因，不能迁入公库。基础工程只用隔离人工样例，不自动写入个人来源。分支、PR、版本与回退规则见[发布与回滚](release-and-rollback.md)，当前交接见[Codex 交接](codex-handoff.md)。

数据目录直接沿用[数据规范](data-conventions.md#文件角色与实际目录)：原文使用 `memory/sources/`，主题页使用 `memory/topics/`；候选、独立记录、运行控制和待确认分别用 `memory/staging/`、`memory/records/`、`memory/runs/`、`memory/pending.md`。不另建 `raw/`、`wiki/` 事实副本，不自动填写现有个人模板。

字段、状态与版本算法只在数据规范维护；通用处理规则在实现明细维护；详细测试步骤在场景与验收维护。本方案只安排任务、依赖和交付，实际阶段状态及验证链接统一更新 Roadmap。

### 2.1 开工时先落实的接口约定

M0-01 确定执行载体后，先为采集、加工、审核、发布和证据读取各准备一组成功／失败的输入输出样例。沿用数据规范中的对象和版本字段，不再定义第二套 schema，也不要求把内部模块部署为 HTTP 服务。

交接至少说清三件事：输入允许读取哪些文件及版本；输出是候选、审核结果、证据集合还是实际保存回执；失败后是否已经产生持久写入、下一步应重试还是先核对远程。尤其把“返回候选”与“正式发布成功”、Git 提交失败与结果未知分开。样例放在 `project/tests/fixtures/`，只能使用隔离材料；真实端到端验收另外记录。

## 3. M0：跑通一条真实链路

执行顺序：**M0-01 → M0-02 → M0-03 → M0-04**。每批完成后记录结果，修复会阻断后续的失败，再进入下一批。

### M0-01：验证执行环境，确定最小实现方式

**输入：** 本方案及不包含真实个人资料的人工隔离样例。

**工作：** 在拟用的手动执行环境验证五项能力：读取限定文件；调用加工与独立 Review；执行程序校验；条件写入测试区域并从远程读回；清理临时工作区后读取持久进度继续处理。同时尽早检查拟用 GPT 云端定时环境的相同能力，区分交互环境与定时环境的工具和权限。

**交付与通过条件：** 一份能力验证记录，写明实际环境、模型调用方式、可访问路径、Git 写入方式、校验器运行位置、持久状态位置和失败原因；据此确定语言、入口与适配方式。凭证通过环境安全配置提供，文档与 Git 中只留配置名称，不保存密钥。

这一批结束时必须明确实际采用的方案、仍被阻塞的能力及下一步，不继续保留一串未选择的框架候选。试跑配置记录单份输入和读取范围上限、单次调用超时、每批容量与有限重试；记录实际调用次数、耗时和可取得的 token 用量。缺失用量不能当作零成本。日常运行按现行audit／continuous-v1策略不设每日或累计调用次数硬门槛，历史有限专项授权单独保留。

手动闭环必需能力缺失时，先解决该阻塞；只有定时环境受限时，可在已确认范围内继续 M0 手动闭环，同时记录 M1 阻塞。若需要改变已选择的云端任务方案，先说明具体限制，再与用户确定替代方案。这里的探测不能代替 M1 的真实每日运行验收。

### M0-02：保存首条真实对话

**输入：** 一段明确获准采集的真实资料；只保留实际提交的原话、说话者、消息顺序和已知时间，不扩大来源范围。工程回归另用明确虚构的人工资料；方案和样例不能替代真实原始证据。

**工作：** 落实来源模板与稳定 ID；保留说话者、消息顺序、实际可见内容和已知时间；保存原文，读回核对，生成来源保存回执。未知时间保持未知。再重复提交相同内容，检查是否复用已有来源。

**交付与通过条件：** 一份真实来源、保存回执、采集及 Git 适配代码。回执把来源 ID 和版本映射到实际 Git 提交及文件路径；能从远程读回同一内容，历史快照可定位；重复提交不多建来源。原文未读回时，入口不能宣称保存成功。

### M0-03：提取、校验、Review 与正式发布

**输入：** M0-02 的固定来源版本及加工、审核规则。

**工作：** 按固定原文实际支持的内容提取记录和主题页变更，先做程序校验，再独立调用模型 Review。不为凑对象数生成决定、范围、期限或完成事实。审核输入包括原文、候选、相关旧记录与规则版本；正式发布前重新核对这些版本及目标仓库状态。互相依赖的记录、Wiki 与发布清单一致提交，读回后补发布回执。

**交付与通过条件：** 候选、审核记录、忠实于固定原文的正式知识记录、主题页、发布回执，以及加工、校验、审核调用和发布控制程序。每项主要结论能定位具体原话，未提供的细节保持未知；Wiki 的新增归纳也经过审核。审核关联字段回填不能触发无限重审，正文、证据等实质内容变化必须重新审核。

隔离样例至少验证：缺失或错配 Review、审核后候选变化、越出允许写入路径时，程序实际拒绝发布，远程正式文件保持不变。检查不能只依靠模型口头承诺。加工与 Review 调用不能获得绕过统一发布入口直接修改正式知识的能力；无法落实这一边界时记录阻塞。

### M0-04：独立问答与本地恢复

**输入：** 已发布文件、对应来源、获准读取范围，以及[三个预设验收问题](scenarios-and-acceptance.md#m0-独立会话验证)。

**工作：** 实现证据读取与回答入口，实际读取已发布记录、主题页和对应原文的正文，并保留相关未加工资料的状态检查。固定同一份限定证据及版本，三个问题分别使用新的独立模型调用，不继承本轮聊天、前题答案或加工／审核上下文；只提供必要规则、限定持久文件及问题，不把标准答案、预期引用或验收文档放进提示。随后从私有远程仓库重新取得本地副本。

**交付与通过条件：** 预先固定的三个来源问题的实际答案、逐项引用核对记录、证据读取与回答代码、本地恢复记录。固定程序、规则、数据与来源／记录／主题页版本，记录各调用实际读取范围、调用 ID、耗时和可取得的用量；模型标识未由 CLI 提供时如实记录 `unknown`。答案来自持久文件，来源版本与片段正确；原文不足以确定的细节、完成状态和原始时间不得补造。未加工资料标明状态；问答前后核对 HEAD、工作区与文件字节，不能写入个人记忆。恢复后的来源、记录、主题页和链接可用，不依赖本次临时目录。长期本地副本的位置在此批落实。

**M0 完成门槛：** 上述四批有实际验证记录；限定真实原文可靠保存，其忠实知识记录和主题页经独立 Review 后发布；按预先固定的三题，脱离原聊天仍能回答并找到准确出处，明确资料缺口与未知时间，问答只读且本地可恢复。问题必须适配实际原文，缺少原话的历史决定不能补造。仅完成模板、提示词、一页摘要或只读证据输出，不算 M0 通过。

## 4. M1：形成可持续使用的知识库

在 M0 通过后执行 **M1-01 → M1-02 → M1-03 → M1-04**。阻断发布安全或数据一致性的问题发现即修复，不留到最后一批才处理。

新运行与控制格式0.4及后续扩展按数据规范兼容，正式对象0.2与来源0.1保持。下列仍是业务验收单位，不能因接口已编写就勾选每日运行或整个M1；实际阶段状态见[Roadmap](roadmap.md)。

### M1-01：多来源自动归类，维护同一主题

**输入：** 用户围绕实际主题提交的文章、其他模型可见对话与本人想法，保留原链接或来源说明，只处理明确范围。M1-01同时覆盖健康&运动、工作事业、学习&能力提升三类新输入、跨领域及无法确定归属的情况；验收素材须实际获准，不为凑分类制造个人事实。

**工作：** 补齐文本、链接和对话适配；正文取不到只保存链接与状态。正常process提取内依据three-domains-v1自动选择health／career／learning，独立Review核对语义，不增加分类调用；新create／update使用不重复的稳定键，可空或跨类，同一事实不复制。无关／通用资料可[]；只有原意需用户决定时needs_confirmation。新内容与旧知识比较并维护同一主题，精确reuse保留旧受审字段／自由标签。knowledge在显式source／run范围生成当前只读领域目录，复用控制、缺口与预算；三个README保留固定入口，不逐次重写或扩大publisher写集。按页首质量批次使用两个显式 Skill 引用、输入画像、覆盖去向、时间限定、派生计算和逐项独立审核；引用解析及校验由程序承担，不能只在提示词中写出 Skill 名称。

**交付与通过条件：** 多来源、自动三领域分类、关联去重与限定当前目录，以及真实知识增量。检查三领域新输入、跨类共享、空／未分类及必要待确认、精确旧reuse、topic精确record版本并集、控制排除和缺口披露；分类策略与规则绑定，同一资料重交不冒称按新规则处理。问答区分文章观点、模型建议与用户选择，无正文不编摘要。新增质量门槛要求实际 Skill 加载和版本绑定、完整且合理的内容去向、有依据的概览与逐项审核均通过。隔离工程通过不等于真实业务或M1整体通过；对应S1、S2、S3、S6、自动领域工程表及 SQ01—SQ11。

### M1-02：补充、纠正与待确认

**输入：** 一次真实补充或纠正，以及需要澄清的具体事项；真实资料未覆盖的冲突分支使用隔离样例。

**工作：** 新表达先保存为来源；在加工前提问，检查它能否影响当前答案。随后区分真实变化与错误纠正，更新直接受影响的记录和 Wiki。登记待确认问题，用户答复保存为新证据并续接原事项；无关通过项继续发布。

**交付与通过条件：** 纠正与依赖更新、待确认续接、读取有效性检查，以及加工前后对照记录。旧错误不再通过原文路径成为当前事实；新原文尚未审核时明确说明；未知时间不补造；相同问题不重复创建；收到答复与知识更新完成分别记录。对应 S4、S5、S7，并检查读取预算不足时能说明未查范围。

### M1-03：接每日任务并完成真实增量验证

**输入：** 已通过的手动流程，用户确定的每日时刻，以及实际定时环境可用的模型、工具、资料范围和权限。

**工作：** 使用daily到production分批／最终审核及answered续接的持久总编排，先完成工程验证，再在实际定时环境用隔离样例跑完整链路：读取 → 加工 → 程序校验 → 独立 Review → 发布控制 → Git 写回与读回。验证通过后，按 `Asia/Shanghai` 每天一次启用同一流程；配置单批容量、执行窗口、调用审计和首次后最多3次重试，持久保存进度，不用每日或累计次数硬上限停止日常加工。

**交付与通过条件：** 调度配置、增量选择与续跑程序、两次真实定时触发及运行回执。两次触发之间加入新增、变更和较早发生的补录资料，并保留允许续跑的未完成项；后一轮能覆盖这些输入，已完成且未变的资料不重复发布。执行窗口结束时持久返回续接信息，结果分清已发布、待确认、失败和剩余范围；容量、速率或服务条件阻塞不能误报已完成。

创建任务、手动触发或只有模型输出，都不代替这两次真实运行。环境限制、权限变化或外部调用失败必须留记录；每日链路未通过时，不把 M1 标为完成。

启用时同时交付状态查询与暂停入口。状态查询对照预期触发时间、实际触发和最近成功结果，能够发现“没有触发”，不能只汇总已有回执；发布异常时能暂停、核对在途提交、修复并复验后再启用。处理规则见[每日调度的状态与停启](implementation-details.md#51-状态查询暂停与重新启用)，对应检查纳入本批与 M1-04。观察开始前固定程序、规则和配置版本；相关修复改变定时链路时，在修复版本重新完成两次实际触发验收。

### M1-04：恢复、删除与第二模型读取

**输入：** 已完成的知识库流程、隔离测试副本，以及用户授权给第二模型的限定资料包和版本。

**工作：** 按[每日运行与恢复验证](scenarios-and-acceptance.md#每日运行与恢复验证)执行以下检查，并修复失败项：

- 审核后候选、来源、相关旧记录或规则变化：旧审核不能放行新内容。
- 并发更新相同对象或无关文件：不覆盖他人修改；影响依据时重新合并和审核。
- 提交成功但回执中断：找到已有提交并补回执，只续跑未完成部分，不重复发布。
- 达到重试上限、临时工作区丢失：任务能够结束，后续从持久状态继续。
- 普通删除：同步处理当前记录、Wiki 和引用，保留必要的禁止重建控制；重跑与问答不恢复已删除内容，Git 历史仍可回溯。
- 第二模型：实际读取与第一模型相同的限定文件和版本，回答同一组事实与来源问题；不能只复述第一模型的答案。

**交付与通过条件：** 恢复和迁移验证记录、通过的关键回归问题、一页日常使用说明。第二模型接入或读取尚未验证时，记录阻塞，M1 保持未通过。使用说明覆盖如何提交、查看保存与整理结果、提问、确认纠正、查看失败以及恢复本地副本；附件只验证链接，不宣称附件本体已备份。

**M1 完成门槛：** 多来源、Skill 引用及知识质量、纠正、待确认、两轮实际每日运行、恢复与第二模型读取全部有通过证据。现场可演示“昨天的资料整理了吗？现在确定了什么、依据是什么、还有什么待确认？”，再提交纠正并验证答案变化；期间资料还应能说明记录覆盖、可比变化及无法判断的范围。测试样例通过不能代替真实端到端演示。

### 5.2 可复现的验收交付

每批验证记录除了结果，还必须给出接手者能直接使用的**实际入口或命令、最小配置名称、输入位置、预期结果和实际输出位置**。这些内容随实现填写；方案中的拟定文件名不算已经存在的运行入口。程序校验、去重、版本门禁和恢复用可重复的自动检查；语义忠实、状态区分及引用准确性用固定问题与证据逐项核对，不能仅凭另一个模型打高分通过。

阶段验收固定代码提交、依赖与配置版本、模型标识、规则版本和样本版本。M0 使用在真实问答前按实际原文固定的三个问题，验收预期仅供事后逐项核对，不进入模型输入；M1 按[首批问题与预期证据](scenarios-and-acceptance.md#首批问题与预期证据)扩展到 5—10 个有真实依据的问题，不用临时改题掩盖失败。M1 每批回归受影响场景，阶段结束再检查 M0 基础闭环。关键失败未修复不得标为通过，延期优化单独说明。

确认程序、模型调用方式或规则改变后，重验受影响项并保留旧结果与原因；涉及每日链路的版本变化按 M1-03 重验。每次运行只采集必要的耗时、调用量、处理结果与剩余范围，不为首版另建监控平台。

### 5.3 每批汇报与阶段收尾

每批交付程序或配置、必要文档和一份验证记录，明确本次可用能力、实际结果和剩余阻塞。运行失败如实记录，修复后复验受影响场景；不因文档已写完就勾选阶段完成。

| 分工 | 负责内容 |
| --- | --- |
| 用户 | 本方案已确认；选定首批真实素材，提供必要资料；在接入时确定每日时刻、资料访问范围及第二模型授权；核对实际体验 |
| 开发执行 | 按批次实现、验证和修复；记录实际证据；遇到改变已确认范围或执行环境的阻塞时提出具体选项 |
| 模型加工与 Review | 按固定输入和规则生成候选、独立审核、组织回答；不以模型解释替代程序校验和实际保存证据 |

M0 验收通过后按已确认范围进入 M1；不要求用户逐条批准常规知识整理，也不为普通实现细节反复暂停。需要改变数据范围、外部模型访问或既定运行方式时，先具体说明影响。

工期在 M0-01 后按实际环境估算。M1 验收必须包含两次每日真实触发及中间资料变化，需要留出跨日观察窗口，不能用连续手动运行压缩替代。

## 6. 当前接续与阶段边界

工程按M0手动闭环、M1多来源与质量、更新、每日运行和恢复迁移推进；日常实现和隔离回归可持续进行。真实来源保存、模型处理及第二模型读取须遵循已有明确范围，只补足确实缺失的材料和运行条件，不能把工程任务自动扩大为全库外发。

接续时阅读公库 AGENTS、总体／四层技术方案、实现明细、数据规范和场景验收；按[Codex 交接](codex-handoff.md)核实际分支、准确受测提交和 CI。双仓核对工具只读检查可见性、同名分支、准确公库 CI、公开工程完整性及私库无活动工程副本；程序从公库加载，实际核心工程 `program_commit` 与私库 `data_head` 分别记录，不同步代码或迁移历史。

下一步依据Roadmap中缺失证据安排：真实多来源／三领域、增量与纠正、pending闭环，目标GPT runner五能力及持久恢复，两轮真实触发和获准第二模型读取。代码包版本、人工样例或公开CI通过均不替代这些出口。阶段发布须满足[发布与回滚](release-and-rollback.md)相应门槛。
