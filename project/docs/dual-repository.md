# 公开代码与私有资料一起使用

## 工作方式

公开仓库是唯一工程来源，保存程序、提示词、版本化通用 Skill、脚本、人工测试、CI、工作流定义及产品／技术设计。采集、知识加工、独立审核、发布、读取、定时编排与复用／恢复均加载公库代码。工程在公开 `dev` 开发，通过审查和准确提交的 CI 后，经 PR 交付 `master`。

私有仓库只保存原文、候选、正式知识及分层、审核、控制、运行数据、私人验证、完整 Git 历史和导航。历史提交及归档保留原工程证据，但不作为当前程序加载。私库不再维护活动代码、规则、测试、CI 或工作流；工程更新不复制回私库。

公开 CI 只运行人工资料测试，不需要私库访问凭据。真实操作从公库 checkout 加载程序，以 `--repo` 指向获准的私库；模型请求／返回、缓存和调用账本保存在私有位置。工程定义归公库不等于已经部署目标 GPT 定时 runner；实际任务和两轮真实触发仍待验收。

## 分支配对

| 用途 | 工程仓库分支 | 私有知识仓库分支 | 对应 runtime 环境标识 |
| --- | --- | --- | --- |
| 开发与验证 | `dev` | `dev` | `dev` |
| 稳定／生产 | `master` | `master` | `prod` |

两边使用独立 checkout，并实际处于同名分支。`dev/master` 和 `master/dev` 都拒绝；初始化 `main`、其他功能分支和 detached HEAD 不参与运行配对。公开 CI 也必须来自这一共同分支，不能因同一提交曾在另一分支通过就借用结果。

同名只确定对应关系，公库准确代码 HEAD、工程完整性、私库资料边界、权限和生产发布条件仍须核对。核对不会切换分支、创建环境绑定或把开发知识发布到生产。两库 Git 提交号与历史独立保留。

## 每次加工前核对一次

需要 Linux、Python 3.11 或 3.12、Git，以及能读取两个仓库和公开 Actions 结果的现有 `gh` 登录。核对脚本随完整 Git clone 提供，代码包不能替代这个工程 checkout。不要把密码或令牌写入命令、Git 或测试资料。

```bash
python3.12 -B /path/to/code/project/scripts/check_dual_repo.py \
  --code-repo /path/to/code \
  --data-repo /path/to/private \
  --code-ref <公开代码的完整提交号> \
  --ci-run <该提交成功的Actions运行ID>
```

两边工作区先保持干净。公库 checkout 必须就是指定受测提交；两边按上表选择同名的 `dev` 或 `master`。入口实时核对：

- 公库可见性为公开，资料库为私有，两个仓库相互独立。
- 指定工程 CI 对应公库准确 HEAD，且推送分支与两边的共同分支一致，六组测试和两组基础检查全部成功。
- 公库核心工程完整有效，私库不含活动 `project/src/`、`project/prompts/`、`project/skills/`、`project/scripts/`、`project/tests/`、`project/ci/`、`pyproject.toml` 或 `.github/workflows/`。私有 `project/validation/` 和历史 `archive/` 保留。

核对失败或核对过程中状态变化即停止，先处理明确的版本、工作区或权限差异。报告包含私库版本信息，只在私有位置保存，不附到公开仓库或公开 CI 日志。入口检查单份公库工程及私库资料边界，不再比对两份核心代码。

## 从公库加载程序

核对只证明报告时点的状态，之后修改工程或切换版本需要重新核对。核对成功后，当前目录和模块路径都指向公库，数据目录指向私库：

```bash
cd /path/to/code
PYTHONPATH=/path/to/code/project/src python3.12 -P -B -m pdm doctor \
  --repo /path/to/private
```

`-P` 避免当前目录中的同名模块覆盖公库程序，`-B` 避免生成字节码。之后按[日常使用](daily-use.md)运行采集、加工和读取，保持公库模块路径及私库 `--repo`。资料授权、模型调用记录、未知结果对账、审核、发布和环境绑定继续生效；只读核对本身不调用模型或启用定时任务。

核对报告中，`code_commit` 是成功 CI 对应的公库 HEAD；`program_commit` 是实际公库核心工程最近提交；`data_head` 是私库资料 HEAD。文档单独更新时，前两者可能不同，准确 CI 仍必须属于当前公库 HEAD。来源、候选及审核保留原程序／规则绑定，不能将旧记录改写为新公库版本。

## 工程更新时

只在公开 `dev` 修改工程，完成审查和准确 CI，再重新执行 `dev/dev` 核对；不再复制代码到私库。稳定交付经 PR 进入公库 `master`，以该准确提交自己的 `master` CI 和私库 `master` 单独核对。私库保留资料、导航、运行绑定、调用账本和真实验证历史，不把开发资料整库覆盖到生产。

历史 Skill 版本保持不可变，新增规则使用新版本。不要 fetch、merge 或 mirror 私库历史到公库，也不要将私库 release 包直接当公开材料，因为其中可包含私人 README。程序回退在公库选择兼容的代码版本，资料及其历史不随工程回退。

## 能证明什么

核对证明公库准确受测工程与当前私库资料边界、分支配对符合要求。人工测试、真实模型质量、真实资料加工、云端部署和定时运行仍各自记录；一次核对成功不代替这些验收，也不启用新的模型或定时任务。
